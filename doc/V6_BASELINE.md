# V6 API Baseline

This document defines the first V6 slice: a repeatable API baseline before adding
cache, changing indexes, or introducing a new queue. The baseline is intentionally
small and comparable. It is not a capacity or stress test.

## Measurement scope

The runner measures three existing authenticated read scenarios:

1. `GET /api/projects?scope=all`
   - project visibility and membership projection;
2. `GET /api/projects/{projectId}/tasks?pageNumber=1&pageSize=20&sortBy=createdAt&sortDirection=descending`
   - total-count query plus ordered pagination and label projection;
3. `GET /api/projects/{projectId}/dashboard`
   - composed task metrics, due-date lists, and recent activity.

The endpoints are deliberately read-only. The selected task query already exposes
the kinds of behavior that V6 must reason about: filtering, ordering, projection,
pagination, and the cost of a count query.

## Preconditions

Run the baseline against a PostgreSQL-backed environment, not an EF Core InMemory
test host. Record these values next to every report:

- commit SHA and application image tag;
- .NET and PostgreSQL versions;
- CPU, memory, storage, and Docker resource limits;
- database connection pool settings;
- database fixture size;
- request parameters and authenticated user's visibility scope;
- warmup and measured request counts.

The first fixture should contain at least:

- one benchmark user;
- twenty visible projects;
- one benchmark project with at least 1,000 tasks;
- a representative distribution of task statuses, priorities, labels, and due dates;
- project activity and notifications representative of the selected read scenarios.

The fixture is a measurement input, not production data. Do not use real user
credentials or real personal data in a baseline environment.

## Running the baseline

Keep the access token outside shell history where possible:

```powershell
$env:V6_BASELINE_ACCESS_TOKEN = '<short-lived benchmark token>'

pwsh -File .\scripts\Measure-ApiBaseline.ps1 `
  -BaseUrl http://localhost:5000 `
  -ProjectId 00000000-0000-0000-0000-000000000000 `
  -WarmupRequests 5 `
  -MeasuredRequests 50 `
  -OutputPath .\artifacts\v6\baseline-local.md
```

Replace the project ID with a project visible to the benchmark user. The token is
used only in memory and is never written to the report. The default output location
is ignored by Git under `artifacts/`.

The runner:

- warms each scenario before measuring it;
- records successful response latency and payload size;
- records non-2xx responses and transport failures;
- calculates p50, p95, p99, average latency, error rate, and sequential throughput;
- writes a Markdown report with the HTTP status distribution;
- exits with code `1` when any measured request fails.

Percentiles are calculated over successful measured requests using the nearest-rank
method. Throughput is measured requests divided by wall-clock duration for a
sequential closed-loop run. It must not be presented as a maximum-capacity result.

## Database evidence

API latency alone cannot explain a database regression. For each representative
query, capture a PostgreSQL plan separately. The repeatable runner
[`scripts/Capture-PostgresQueryPlans.ps1`](../scripts/Capture-PostgresQueryPlans.ps1)
captures the current task, dashboard, and activity paths:

```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
-- paste the parameterized SQL generated by the selected EF Core query
;
```

Keep the plan, parameter values (with identifiers anonymized), row counts, and
execution environment beside the baseline report. Prefer SQL generated from the
current store implementation or the focused diagnostic described in
[`V6_QUERY_ANALYSIS.md`](./V6_QUERY_ANALYSIS.md); do not invent a query that does
not represent the production code path.

## Comparison rule

Do not claim an optimization worked unless the before and after runs use the same:

- fixture and database state;
- application and infrastructure limits;
- request parameters and warmup policy;
- number of measured requests;
- measurement runner version.

The next V6 slice should be chosen from the first measured bottleneck. Cache, Redis,
new indexes, and queue changes remain out of scope until the baseline identifies a
specific problem and a measurable success threshold.
