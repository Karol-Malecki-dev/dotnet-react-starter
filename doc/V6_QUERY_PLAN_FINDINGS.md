# V6 Query-Plan Findings

## Evidence run

The first reproducible evidence run was captured on **2026-09-22** with:

- PostgreSQL 16.13 on Alpine Linux;
- disposable Testcontainers database;
- 20 noise projects;
- one benchmark project with 1,000 tasks;
- two labels per task;
- 200 recent activity rows;
- natural PostgreSQL planner decisions, without `enable_seqscan = off`.

The report is generated by
`PostgreSqlQueryPlanEvidenceTests.PostgreSql_query_plan_evidence_is_captured_for_v6_fixture`
and is written to the ignored `artifacts/v6/` directory. The exact generated report
contains the fixture identifiers and should not be committed.

## Observed plans

| Query path | Execution time | Observed access path | Interpretation |
|---|---:|---|---|
| Visible project list | 0.122 ms | Sequential scan of 21 projects, then sort | Expected at this fixture size; no index change is justified. |
| Project task count | 0.240 ms | Index-only scan using `IX_ProjectTasks_ProjectId`, 1,000 heap fetches | The project filter is indexed; visibility-map effects should be measured only with a larger or vacuumed fixture. |
| Task page with labels | 1.034 ms | `IX_ProjectTasks_ProjectId`, top-N sort, then `IX_ProjectTaskLabels_ProjectTaskId_Name` | The current query reads 1,000 task index entries to return 20 rows. A `(ProjectId, CreatedAt)` index is a hypothesis, not an approved change. |
| Dashboard statistics | 0.432 ms | `IX_ProjectTasks_ProjectId` | The aggregate is sub-millisecond with 29 shared buffer hits. |
| Dashboard overdue tasks | 0.492 ms | `IX_ProjectTasks_ProjectId`, filter, top-N sort; 835 rows removed | The existing `(ProjectId, Status, DueDate)` index is not selected naturally for `Status <> 'Done'` at this scale. |
| Dashboard upcoming tasks | 0.559 ms | `IX_ProjectTasks_ProjectId`, filter, top-N sort; 822 rows removed | Same signal as overdue tasks; a partial `(ProjectId, DueDate)` index is only a future hypothesis. |
| Recent project activity | 0.073 ms | Backward scan using `IX_ProjectActivities_ProjectId_CreatedAt`, then primary-key user lookup | The existing activity index matches the read path. |

## Decision

No production query or index change is approved from this run. Every measured path
completed in approximately 1.1 ms or less on a warm disposable database, so adding
an index now would increase write/storage complexity without proving a user-visible
benefit.

The two useful hypotheses are:

1. task pagination may benefit from `(ProjectId, CreatedAt DESC)` when a project
   contains substantially more than 1,000 tasks;
2. dashboard due-date lists may benefit from a partial
   `(ProjectId, DueDate)` index with `Status <> 'Done'` when the filtered task
   population is large.

Both hypotheses require a larger fixture and an API latency comparison before
implementation. The existing composite dashboard index must not be removed or
replaced based on this report alone.

## Large-fixture follow-up

The opt-in
`PostgreSqlLargeFixtureApiBaselineTests.PostgreSql_large_fixture_api_baseline_is_captured`
now repeats the measurement with 10,000 tasks, 20,000 labels, and 2,000 activity
rows. It exercises the three authenticated read-only API scenarios and captures
plans for the task page and dashboard paths in the same Testcontainers database.
The detailed protocol and recorded API p95 values are documented in
[`V6_LARGE_FIXTURE_API_BASELINE.md`](V6_LARGE_FIXTURE_API_BASELINE.md).

The larger run still does not approve an index migration:

- task-page plan execution was 7.589 ms and used the existing project task index
  followed by a top-N sort;
- dashboard statistics executed in 3.946 ms with the existing composite index;
- overdue and upcoming queries executed in 1.417 ms and 1.711 ms respectively,
  using the project/date portion of the index while filtering `Status <> 'Done'`;
- the authenticated API p95 values were 30.022 ms for the task page and
  39.321 ms for the dashboard, with no failed requests.

The API-to-plan gap should be separated into database time, EF materialization,
and endpoint orchestration before introducing cache or changing the schema.

## Next measurement

The next performance slice should:

1. capture the generated EF SQL for the authenticated API endpoints;
2. define a measurable p95 and plan-quality threshold for one candidate change;
3. compare that candidate in a disposable database with the same 10,000-task fixture;
4. record p95 latency, execution time, rows removed by filters, and buffer reads;
5. adopt a migration only if the before/after result meets the documented threshold.

Until that measurement exists, cache, Redis, and speculative index additions remain
out of scope.
